# PRI - Project

Search system for short-term rentals (Airbnb) in Porto and Lisbon.
It combines the Inside Airbnb listings and reviews with OpenStreetMap points of interest and Wikipedia articles about those places.

## Setup
Requires make, bash, curl, Docker and python 3.12+. On Windows, install make with `winget install ezwinports.make` and run it from Git Bash.

```
python -m venv .venv
.venv/bin/python -m pip install -r scripts/requirements.txt   # Windows: .venv/Scripts/python
make            # collect, process and analyze
```

**make collect**: downloads the raw data into data/raw/. It takes about 20 minutes, almost all of it fetching Wikipedia. If it is interrupted, run it again and it resumes.

**make process**: cleans the raw data and builds the document collection in data/processed/ (see [Processed data](#processed-data)).

**make translate**: translates the reviews in French, Spanish, Portuguese, German, Italian and Dutch to English, locally on the CPU. It takes about 10 hours. If it is interrupted, run it again and it resumes. The Solr indexing skips reviews that have no translation yet.

**make solr-up**: starts Solr in Docker and waits until the `airbnb` core answers. The admin interface is at http://localhost:8983. **make solr-down** stops it and keeps the index.

**make index**: starts Solr if needed, defines the schema of both setups (see [Solr setups](#solr-setups)) and reindexes everything in each. For a quick test: `make index ARGS="--limit 500"`.

**make run-queries**: starts Solr if needed and runs the queries IN1, IN2, IN3 and IN5 (`scripts/queries/inN.setupM.json`) on both setups. It writes the TREC run files `runs/setup1.run` and `runs/setup2.run`, one line per result (`qid Q0 docid rank score runid`), with up to 100 results per query. Run `make index` first.

To run the complete exploratory analysis and regenerate the CSV tables and PDF figures:

```
make analyze
```

The two analysis notebooks are executed with `jupyter nbconvert`; the `Makefile` uses
the `.venv` Python automatically when that environment exists.

## Structure
```
Makefile                        data pipeline (make collect downloads the raw data)
scripts/osm_query.overpass.in   Overpass query, @BBOX@ is replaced by each city's bounding box
scripts/fetch_wikipedia.py      fetches Wikipedia articles
data_processing.py              cleans the raw data and builds the documents (make process)
scripts/translate_reviews.py    translates the reviews to English (make translate)
docker-compose.yml              Solr container (make solr-up, make solr-down)
scripts/solr_index.py           defines the Solr schema and indexes the documents (make index)
scripts/solr_analysis.py        Solr text analysis and synonyms
scripts/solr_query.py           runs a query file on one or more setups
configs/                        one file per Solr setup (schema, analyzers, qf/pf, boosts)
docs/schema.md                  Solr schema and indexing decisions
docs/report_solr_schema.md      report section: document model, schema, language analysis, setups
data/raw/                       raw data
data/processed/                 processed data
```

## Data
The raw data is not tracked by git.

### Sources

- data/raw/airbnb_porto and airbnb_lisboa: Inside Airbnb (https://insideairbnb.com/get-the-data/)
- data/raw/osm: OpenStreetMap via the Overpass API
- data/raw/wikipedia: Wikipedia

### Files

**Inside Airbnb**
- listings.csv.gz: listings, 90 columns (description, neighbourhood, coordinates, price...). Porto ~15k, Lisbon ~25k.
- reviews.csv.gz: listing_id, id, date, reviewer_id, reviewer_name, comments. Porto ~1,1M, Lisbon ~1,9M
- neighbourhoods.geojson: neighbourhood boundaries (coordinates).

**OpenStreetMap**
- pois_porto.json and pois_lisboa.json: Overpass response.
Categories:
  - food and drink
  - tourism and heritage
  - transport (stations, metro, bus stops)
  - shops (supermarkets, bakeries, convenience)
  - leisure (parks, beaches)
  - public parking

**Wikipedia**
- articles.jsonl: one article per line with qid, lang, title, text (usually the article body), url,
  revid and pois.
- Fetched with the Wikidata API and the Wikipedia TextExtracts
  API.

### Processed data

Generated by `make process` in data/processed/:

- listings_clean.csv: active listings (at least one review in the 3 years before the snapshot `DATE`), HTML removed from the text, price as a number and amenities as a JSON list.
- reviews_clean.csv: reviews of those listings with at least 50 characters after removing HTML, with their language in `lang`.
- pois_clean.csv: named OSM POIs with category, type and the linked Wikipedia article.
- wikipedia_clean.jsonl: Wikipedia articles without the final sections (References, External links, See also, Bibliography).
- proximity.csv: listing_id, osm_id and distance_m for the POIs within 500 m of each listing (the 5 nearest per category, plus every POI with a Wikipedia article).
- documents.jsonl: one document per listing, with `reviews` and `pois` as nested (child) documents, in the Solr JSON format.
- reviews_en.jsonl: English translation of the non-English reviews, one `id` and `text` per review (generated by `make translate`).

## Solr setups

The documents are indexed in two comparable setups, each defined by one versioned file (schema, analyzers, `qf`/`pf`, boosts). `docker-compose.yml` creates one core for each.

| | `configs/setup1.json` | `configs/setup2.json` |
|---|---|---|
| Core | `airbnb_s1` | `airbnb_s2` |
| Documents | listings only | listings with nested reviews and POIs (block join) |
| Analysis | one simple analyzer | English for the description and the (translated) reviews, Portuguese for Wikipedia, synonyms |
| Ranking | edismax on name, description, host_about | the same, plus review and POI evidence and a rating/popularity boost |

```
make index                                       # both setups; ARGS="--limit N" for a sample
python scripts/solr_index.py --setup configs/setup2.json --reset     # one setup
python scripts/solr_query.py scripts/queries/rural_quiet.json --setup configs/setup1.json configs/setup2.json
```

The query files in `scripts/queries/` only hold the text, filters and fields, so the same file runs on both setups.
The classification of the fields (searchable, filterable, display only), the language analysis justified with the EDA and a worked example are in [docs/report_solr_schema.md](docs/report_solr_schema.md); the field list of setup 2 is in [docs/schema.md](docs/schema.md).
